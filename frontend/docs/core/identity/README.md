# Архитектура и Документация Ядра: Модуль `identity`

## 1. Для чего и зачем нужен этот модуль?
В типичных мессенджерах личность пользователя привязана к номеру телефона или централизованному серверному аккаунту (Telegram ID, Signal SMS, WhatsApp). Это фатальная уязвимость:
1. Номер телефона контролируется оператором связи и спецслужбами (перехват СМС через SS7, клонирование SIM).
2. Сервер может подменить публичные ключи собеседника (Man-in-the-Middle) без вашего ведома.
3. При компрометации устройства злоумышленник может «откатить» состояние аккаунта назад (Rollback Attack), чтобы перехватить новые сообщения по старым ключам.

Модуль `identity` реализует **суверенный криптографический паспорт** и управление ключами пользователя на базе мнемонических фраз BIP-39, аппаратной иерархии ключей и монотонных крипто-паспортов с защитой от отката.

---

## 2. Что делает модуль (Анатомия и Архитектура)?

### 1. Генерация Сид-фразы и Корневых Ключей (`mnemonic.rs`)
- Использует стандарт **BIP-39**: 24 криптографических слова на английском языке (256 бит энтропии CSPRNG).
- 256 бит энтропии преобразуются через HMAC-SHA512 (PBKDF2 с 2048 итерациями) в 512-битный мастер-сид (`Seed512`).
- Из мастер-сида через доменно-разделённую деривацию (HKDF с солью и контекстом `anongram-identity-master-v1`) синтезируются мастер-ключи подписи и шифрования.

### 2. Паспорт Пользователя (`passport.rs` & `PassportBlob`)
Паспорт AnonGram — это самоподписанный контейнер идентичности пользователя:
- **`user_id`**: 32-байтный уникальный идентификатор (SHA-256 хеш мастер-публичного ключа).
- **`version` (Монотонный счётчик)**: 64-битное строго возрастающее целое число (`u64`). Каждый раз при обновлении профиля, ротации ключей или смене доверенных устройств версия увеличивается на 1. 
  - **Защита от Rollback-атак**: Клиент AnonGram никогда не примет паспорт с версией `<= current_version`. Если злоумышленник попытается скормить старую копию паспорта с скомпрометированными ключами — ядро мгновенно отбросит её с ошибкой `RollbackDetected`.
- **`hybrid_pubkey`**: Набор открытых ключей пользователя (классический Ed25519 + постквантовый ML-DSA-87 для подписи; X25519 + ML-KEM-1024 для KEM-обмена).
- **`device_pubkeys`**: Реестр авторизованных устройств.
- **`signature`**: Гибридная цифровая подпись самого паспорта мастер-ключом владельца.

### 3. Разделение Ключей: Мастер-ключ vs Ключи Устройств
- **Master Key (Золотой уровень)**: Выводится напрямую из BIP-39. Должен храниться в холодном виде (или защищённом аппаратном анклаве Secure Enclave / Titan M). Он подписывает и валидирует сам паспорт.
- **Device Key (Рабочий уровень)**: Генерируется локально на каждом телефоне/ноутбуке. Мастер-ключ авторизует `DeviceKey`, добавляя его в паспорт. При утере телефона устройство можно отозвать через обновление паспорта, не раскрывая мастер-сид.

### 4. Доверенное сопряжение OTP блокнотов (`PadManifest`)
Модуль управляет манифестами одноразовых блокнотов (One-Time Pads):
- **Gold Shield (Кабель / Прямой контакт)**: Физическая передача ключей блокнота через USB OTG, microSD или локальный защищённый канал. Максимальный уровень доверия. Манифест подписывается мастер-ключами обоих участников.
- **Blue Shield (Беспроводной квантово-устойчивый обмен)**: Обмен ключами по воздуху с защитой через гибридный KEM (ML-KEM-1024 + X25519) и гибридную подпись.

---

## 3. Изоляция и Надежность
* `identity` зависит **только от модуля `crypto`**. Он не имеет доступа к сети, дисковому вводу-выводу или UI.
* Ошибки строго типизированы через `IdentityError`:
  - `MnemonicInvalidWordCount` / `MnemonicChecksumError`
  - `RollbackDetected { expected_min, got }`
  - `InvalidSignature`
  - `Crypto(CryptoError)`
* Все секретные мастер-структуры очищаются при дропе через `zeroize`.
