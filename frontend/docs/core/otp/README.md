# Архитектура и Документация Ядра: Модуль `otp`

## 1. Для чего и зачем нужен этот модуль?
Абсолютно любой алгоритм с открытым ключом (RSA, ECC, даже постквантовый ML-KEM) и любой блочный шифр (AES, ChaCha20) являются **условно стойкими** — их безопасность базируется на предположении о сложности математических задач (дискретный логарифм, факторизация, обучение с ошибками LWE) или на предположении, что у злоумышленника нет суперкомпьютера с триллионами кубитов.

Существует только один вид шифрования во Вселенной, обладающий **доказанной абсолютной криптографической стойкостью (Perfect Secrecy, теорема Клода Шеннона, 1949 г.)** — это **Одноразовый Блокнот (One-Time Pad, OTP)**.
Если сообщение замаскировано истинно случайным ключом той же длины, и ключ используется ровно один раз:
- Даже суперкомпьютер с бесконечной вычислительной мощностью **физически не способен** расшифровать текст: любой осмысленный текст той же длины равновероятен.

Модуль `otp` реализует промышленный, отказоустойчивый одноразовый блокнот для AnonGram.

## 2. Что делает модуль (Анатомия и Архитектура)?

### 1. Двустороннее выделение пространства (`SideA` и `SideB`)
Ключевая проблема наивных реализаций OTP — это рассинхронизация и коллизии (reuse of pad key stream). Если двое собеседников одновременно отправят сообщения, используя один и тот же участок блокнота:
$C_1 \oplus C_2 = (P_1 \oplus K) \oplus (P_2 \oplus K) = P_1 \oplus P_2$
Это катастрофическая уязвимость (Two-Time Pad), позволяющая раскрыть оба сообщения.

**Решение модуля `otp`**:
- При сопряжении двум контактам назначаются несимметричные стороны: **Side A** (Инициатор) и **Side B** (Отвечающий).
- **Side A** расходует блокнот **с головы (offset 0 $\to$ вперед)**.
- **Side B** расходует блокнот **с хвоста (offset FileSize $\to$ назад)**.
- Даже при одновременной активной переписке указатели встретятся только тогда, когда весь объем блокнота (например, 1 ГБ или 10 ГБ) будет полностью исчерпан. Никаких коллизий быть не может.

### 2. Квота резервирования (20% Emergency Reserve)
- Когда указатели Head и Tail сближаются так, что остается менее 20% свободного объема файла, ядро переключается в режим **Reserved Quota Warning**.
- Эти 20% резервируются исключительно под экстренные сигнальные сообщения (SOS, экстренная ротация ключей, аварийный маяк). Обычные тяжелые сообщения блокируются с ошибкой `QuotaExceeded`.

### 3. Аутентификация Вегмана-Картера (Wegman-Carter Poly1305 MAC)
Классический шифр Вернама ($C = P \oplus K$) защищает только конфиденциальность, но не целостность: атакующий в канале может инвертировать биты в шифротексте.
- Для каждого сообщения из текущего среза блокнота берутся дополнительные 32 байта истинно случайного ключа:
  - 16 байт используются как одноразовый ключ $r$ для универсального хеширования Poly1305.
  - 16 байт используются как одноразовая маска $s$.
- Это обеспечивает **теоретико-информационную аутентификацию (Wegman-Carter Authentication)**: подделать сообщение невозможно даже теоретически.

### 4. Аппаратное затирание на диске (Anti-Forensics & Zeroization)
- Как только фрагмент блокнота прочитан и использован для шифрования или расшифровки, он **немедленно перезаписывается криптографическими нулями** (`0x00`) прямо в файле на носителе.
- Вызывается принудительный системный сброс буферов ядра ОС: `sync_data()` / `fsync()`.
- Даже если телефон изымут через 5 секунд после получения сообщения и отправят на экспертизу в криминалистическую лабораторию со снятием чипа флеш-памяти (chip-off forensics) — ключа для расшифровки сообщения **физически не существует в природе**.

## 3. Изоляция и Надежность
* Модуль `otp` полностью изолирован от сетевых сокетов и интерфейсов.
* Ошибки типизированы в `OtpError`:
  - `PadNotFound`
  - `Exhausted` (блокнот полностью израсходован)
  - `CollisionDetected`
  - `IntegrityCheckFailed`
  - `Io(std::io::Error)`
* Автоматически поддерживается atomic state cursor: позиция указателей сохраняется надёжно без риска повреждения метаданных при отключении питания.
